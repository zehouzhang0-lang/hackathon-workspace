# 抖音成交诊断 Agent · Demo 验收与建议排期

更新日期：2026-08-27。

**文档性质：赛前规划，所有验收项均待实现、待检查。** 第 5 题是优先方向，尚未确认官方认领；本文不代表已有应用、已接入 MoneyAI 或已验证需求与经营效果。“48 小时”和“5 分钟”分别是暂定规划标签与路演排练目标，不是已确认的开发时长或性能承诺。

产品定位与规则核验背景见 [产品方案](PRODUCT_BRIEF.md)。本文只定义首版如何判断“能够诚实地演示”。

## 1. 开工门槛

在确认以下事项前，仅整理准备材料，不开展参赛实现，也不默认这些赛前材料获准带入现场。

- [ ] 确认具体赛事、第 5 题的正式要求与认领结果。
- [ ] 确认赛前材料、现场从零创作、官方账号及工具的使用规则；确认是否允许自建前端、外部模型或 API。
- [ ] 确认实际可开发时间、提交截止时间、路演时长及提交形式。
- [ ] 获取获准使用的 MoneyAI 账号和官方说明，确认现场权限；不在仓库、截图或演示日志中暴露密钥。
- [ ] 确认一个行业、一个商家案例及资料使用权限；没有获准的真实资料时，使用明确标识的虚构案例。
- [ ] 确认团队成员、技能与分工后，再决定实现方式；本计划不预设团队人数或技术栈。

若题目认领、工具限制或现场权限与当前方案冲突，先调整范围。尚未核验 MoneyAI 的接口和长期记忆能力，不能将其当作已具备的前提。

## 2. 最小演示范围：六块

验收时保留实际结果及截图或记录，并标记检查时间、使用的平台和已知限制。勾选必须来自实际检查，不能仅凭界面存在或提示词写完。

### 2.1 经营者输入

- [ ] 可录入行业、产品、客单价及币种、目标客户、账号定位、购买入口、咨询与成交情况。
- [ ] 支持填写近期最多 7 条视频的标识、发布时间、内容描述及可取得的核心数据；不足 7 条仍可继续，但提示样本有限。
- [ ] 各指标记录来源、单位、统计对象、时间窗和采集时间；未知值保留为“未提供”，不以 0 代替。
- [ ] 没有账号或后台访问权限时使用手填或粘贴资料；仅输入账号/视频链接时，明确“未读取链接内容或后台数据”，不生成虚构采集结果。
- [ ] 虚构案例在输入、诊断报告、复诊对照及导出材料中持续显示“虚构演示数据”；真实资料只使用获准的脱敏内容。

最小检查：提交一份完整案例和一份缺少留存、咨询来源的案例，两者都能继续，但后者明确列出缺项。

### 2.2 五维诊断

五个维度固定为：**人群定位、内容留存、流量质量、产品报价、成交承接**。

- [ ] 每个维度给出“有观察支持 / 待补充 / 暂未发现明显问题”等状态，并说明所依据的输入；“暂未发现”不等于已排除问题。
- [ ] 每条判断区分“已提供的观察”和“待验证的问题假设”，引用具体视频标识、字段或匿名反馈，并指出证据缺口。
- [ ] 不把未观看的视频、未取得的后台数据、模型猜测写成事实；单凭价格不能认定“太贵”，单凭播放少不能认定“限流”。
- [ ] 不使用无出处的行业阈值、健康分、行业排名或成功概率。若采用外部基准，须有可核对来源、适用范围和一致口径；首版可完全不使用此类基准。

最小检查：删去某一维度的依据后，该维度变为待补充或收窄结论，不能继续沿用原来的确定性判断。

### 2.3 最多三个优先问题

- [ ] 输出 0—3 个优先验证的问题，不强行凑满 3 个；证据不足时可以只给补充资料清单。
- [ ] 每个问题展示问题假设、支持观察、证据引用、缺口和排序理由；按本案例的证据强弱、潜在影响路径与执行成本解释顺序。
- [ ] 不将相关性写成因果，不将“最值得先验证”表述成“已找出唯一不出单原因”，不编造置信概率。

最小检查：输入只支持 2 个问题时只输出 2 个；只提供账号链接时，不能凭空列出 3 个成交断点。

### 2.4 对应行动

- [ ] 每个优先问题至少对应 1 个具体动作，说明改哪里、改成什么、由谁执行，以及下一次要收集什么证据。
- [ ] 每个动作注明观察口径和复查条件；缺少基线时，第一步是建立基线，不承诺提升幅度或成交结果。
- [ ] 内容选题或话术示例只服务于某个诊断问题，不另扩展为完整运营系统。
- [ ] 执行状态由经营者确认；没有确认时显示“待确认”，不会默认已经执行。

最小检查：从一条建议能追溯到对应问题与输入证据，并能明确下一次复诊需要补哪项数据。模糊的“优化内容、提高转化”不能通过验收。

### 2.5 拟用 MoneyAI 的长期记忆

**当前状态：能力、接口和授权尚未核验。** 真实接入与演示存储分开验收。

拟保存的最小内容：商家标识与定位、带来源和时间的数据快照、历史问题及证据、建议动作、经营者确认的执行状态、复诊记录。保留各次记录，不用新结果悄悄覆盖旧结果。

| 检查内容 | 可检查的通过条件 |
| --- | --- |
| 实际保存 | 在获准的 MoneyAI 环境中保存商家 A 的一次诊断及动作，留有可核对记录；不是只在当前对话中复述 |
| 跨会话读取 | 结束原会话后，在新会话通过商家标识读取历史；演示过程中不手动重新粘贴那段历史 |
| 历史参与复诊 | 本次报告明确引用上次问题、动作与执行状态，说明这些历史信息如何影响本次建议 |
| 商家隔离 | 切换到商家 B 后不能读取 A 的记录，未知商家不能误匹配其他档案 |
| 失败可见 | 保存或读取失败时明确报错或标为不可用，不声称“已记住”；恢复后再检查 |

- [ ] 上表检查完成后，才可按实际验证范围描述 MoneyAI 接入；还需确认保留范围、修改/删除方式和调用限制。
- [ ] 若规则允许使用本地文件、数据库或浏览器缓存替代，界面、报告和口播均写“演示存储：本地保存；MoneyAI 尚未接入/验证”。这只通过演示存储检查，**不能通过 MoneyAI 长期记忆验收**。
- [ ] 不把预先拼接历史、手工粘贴旧报告或当前会话上下文冒充跨会话记忆；不演示尚未实现的自动定时跟进。

### 2.6 二次复诊对比

- [ ] 先读取上次档案，再输入动作执行情况与新数据；输出“上次问题、本次观察、下一步动作”三项对照。
- [ ] 计算比率前检查分子、分母对应同一对象与统计口径，并核对时间窗；分母为 0 或缺失时显示“无法计算”，不以 0% 代替。
- [ ] 跨期比较使用可比的观察长度和数据成熟时间，记录自然/付费流量、价格、投放、产品等变化。不能把不同时间窗、不同来源或不相连的漏斗阶段直接相除。
- [ ] 条件不可比时分别展示数据并解释原因，不给增长率或改善结论；样本小时提示不确定性。
- [ ] 未执行或未确认执行的动作不能被判为无效；有变化也不直接归因于该动作或本产品。
- [ ] 下一步允许“继续观察”“调整动作”或“先补证”，理由能追溯到本次数据和历史记录。

最小检查：更改一项历史执行状态或新数据后，复诊能够反映其影响；不能每次只重复首次建议。

## 3. 必过的异常与诚实性检查

下表数字与场景均为**虚构测试输入**，只用于验收行为，不是行业基准、真实商家表现或效果证据。

| 检查场景 | 应观察到的结果 |
| --- | --- |
| 只有账号链接，没有内容或后台权限 | 提示手填资料，不声称已抓取，不编造指标或诊断 |
| 只支持 2 个问题，另 3 个维度缺数据 | 只列 2 个优先问题，其余明确待补充；不为报告完整而补造第三项 |
| 有效咨询人数为 0，或该字段缺失 | 咨询后成交率显示“无法计算”，区分真实零值与缺失值 |
| 两批有效咨询用户分别为 20、30 人，各自同样观察 7 天后成交 2、3 人，来源和口径一致 | 两个咨询后成交率均为 10%；不能把成交人数增加写成转化率提高，也不能证明产品有效 |
| 一期为发布后 1 天播放，另一期为发布后 7 天播放；或两期投放条件不同 | 标记不可直接比较或明确混杂因素，不简单推出内容已改善 |
| 商家 A 保存后新开会话；随后切换商家 B | A 的历史可按实际存储方式读取并参与复诊，B 不出现 A 的记录；平台未验证则如实标明 |
| 记忆读取失败或动作尚未执行 | 不伪装读取成功，不编造历史；不把未执行动作判成失败 |

报告可以使用证据卡、动作清单和前后对照表。没有数据支撑时不画增长曲线，不为填满图表而插值或生成虚构指标。

## 4. 五分钟路演流程（建议，待排练）

先确认正式路演时长是否允许；以下仅是一版 5 分钟脚本。所有虚构案例、预载数据、预计算结果或录屏必须当场说明，且使用方式符合比赛规则。

| 时间 | 演示动作 | 需要让观众看到的证据 |
| --- | --- | --- |
| 0:00—0:30 | 描述一个已在做抖音、却不知道优先改什么的经营场景；交代案例来源 | 真实资料的授权与脱敏说明，或醒目的“虚构演示数据”标识；不声称需求已经验证 |
| 0:30—1:10 | 展示商家资料、视频数据、咨询成交与缺失项 | 数据来源、时间窗、指标口径；演示无权限时如何手填 |
| 1:10—2:10 | 展示五维检查和最多三个优先问题，展开第一项 | 从输入观察到问题假设的依据，以及尚缺什么证据；不是只展示漂亮分数 |
| 2:10—3:00 | 展示第一优先动作和复查方式，记录经营者确认的执行状态 | 具体修改内容、执行人、待观察指标；没有成交承诺 |
| 3:00—4:20 | 在另一会话读取历史，输入第二期资料并复诊 | 上次问题和动作确实被读取并用于建议；数据可比性与限制。如果只有本地演示存储，明确说尚未验证 MoneyAI |
| 4:20—5:00 | 总结可展示的闭环与下一步验证 | 已完成与未完成能力分开；说明还需验证使用价值、付费意愿及实际经营效果 |

第二期数据可以事先准备，但不能把虚构的后续数据说成现场执行动作后产生的真实效果。若有预计算或录屏备用，不能冒充现场生成或实时调用。

建议收尾：

> 我们希望让每次经营调整都有依据和记录：先明确最值得验证的问题，再记录行动，最后带着历史复诊。今天演示的是诊断与复查流程；能否改善经营结果，还需要在获准的真实案例中继续验证。

只有完成第 2.5 节实际检查后，才补充“已通过 MoneyAI 读取历史并用于复诊”的演示说明。

## 5. 相对排期（建议）

**第一门槛仍是题目认领、官方工具规则和现场权限。** 比赛时间与团队技能未知，不将“48 小时”直接当作连续可用的开发时间。以下比例以确认后的可用开发窗口为准；小时数只在确有 48 个可用小时的假设下成立，应预留休息及提交缓冲。

| 顺序 / 占可用窗口 | 48 小时假设示例 | 交付检查 |
| --- | --- | --- |
| 开工门槛 | 开始前确认 | 完成第 1 节；无法确认时不进入实现 |
| 前 15% | 约 0—7 小时 | 核验 MoneyAI 保存、跨会话读取与隔离能力；确定一个案例及其来源。平台验证失败时立即明确缺口，不留到最后 |
| 15%—45% | 约 7—22 小时 | 在获准环境打通输入、五维检查、问题与动作；用缺数据案例验收 |
| 45%—70% | 约 22—34 小时 | 完成并检查实际可行的历史保存与复诊；MoneyAI 和替代存储使用不同的完成状态 |
| 70%—85% | 约 34—41 小时 | 跑完第 3 节异常检查，核对指标、证据、案例标识与商家隔离 |
| 最后 15% | 约 41—48 小时 | 冻结范围、计时排练、复核实际演示、整理限制和提交材料；按真实截止时间留出提交缓冲 |

若窗口更短，按比例压缩并减少视觉装饰和额外选题；不能通过取消数据边界、伪造记忆能力或隐瞒未完成项来“补齐”演示。

## 6. 提交前判定

- [ ] 六块的实际完成状态与验收记录一致，未实现项明确列出；没有把计划或静态页面当作已运行功能。
- [ ] 不接入抖音平台 API、不自动采集后台、不自动发布或投放、不扩展成全功能运营后台。
- [ ] 所有比率、对照与问题都有可追溯输入；无出处阈值、虚构概率和无依据结论已移除。
- [ ] MoneyAI 是否真实接入、哪些能力通过检查、失败时怎样降级，都有明确说明。仅有演示存储时，不把官方平台记忆要求标为已满足。
- [ ] 虚构数据标识、真实资料权限、商家隔离及密钥保护检查完成。
- [ ] 路演不宣称已验证需求、因果效果、商业价值或成交结果；实际演示耗时经过计时，超出时按规则调整脚本。

上述条件用于约束最小演示的可信度，不替代主办方最终验收或评分规则。
